# 🧠 Memory & Context

> **Frontera de uso (Memory vs. Tasks):**
> - `task.md` → progreso **operativo**: checklist de tareas, Snapshot de Contexto (el paso exacto siguiente), y estado de la sesión.
> - `memory.md` → contexto **cualitativo y temático**: conocimiento persistente, decisiones técnicas profundas, lecciones, y el área del producto en foco (no el paso específico).
> Si hay info que sirva para los dos, prioriza: datos con fecha/paso exacto → `task.md`; razonamiento/por-qué/lecciones → `memory.md`.
>
> *Instrucción para la IA: Consulta este archivo al inicio de cada sesión para recuperar el hilo técnico. Actualiza las secciones correspondientes cuando el workflow lo indique (triggers en `/plan`, `/build`, `/test` y gate en `/ship`).*

## ⚠️ Lecciones Aprendidas / Errores Evitados
*Notas sobre bugs específicos, configuraciones que fallaron o refactors intentados para no repetirlos.*

- **[Feedback de Usabilidad]**: Es mejor integrar los conceptos nuevos (como Evals) en las fases existentes (`/test`) y delegar los modos de ejecución (Conductor/Orquestador) de forma implícita, en lugar de sobrecargar al desarrollador final con configuraciones complejas o preguntas confusas.
- **[Estructura de Onboarding]**: En proyectos existentes con archivos raíz consolidados (como `README.md` y `CHANGELOG.md`), es preferible descargar el framework completo en una subcarpeta dedicada (`dbv-specs-ops/`) e indicar al agente su ubicación a través de un archivo de activación ligero (`CLAUDE.md`, `GEMINI.md`). Esto evita colisiones de archivos y mantiene limpio el código de producción.
- **[Preferencia de Commit]**: Para los mensajes de git commit en este proyecto, usar siempre el formato conciso "Version v.X.Y.Z" (ejemplo: `Version v.2.7.0`) en lugar de mensajes largos de Conventional Commits.
- **[Declarar una regla no basta]**: `<coding_standards>` de `MASTER_PROMPT.md` llevaba la regla "un solo `return` + guard clauses" marcada como obligatoria desde v2.0.0, y aun así aparecía código real con 5-6 `return` por función. Una instrucción *advisory* sin un paso de revisión que la audite explícitamente, o un guardarraíl determinista que la haga imposible de saltar, no garantiza cumplimiento — de ahí que `docs/REVIEW.md` ahora la comprueba función por función en el pase "Cumplimiento", y `docs/GUARDRAILS.md` documenta una heurística pre-commit de respaldo.
- **[Este repo no se auto-aplica el ciclo de fases]**: `dbv-specs-ops` es el repositorio que *define* el framework, no un proyecto consumidor. Aunque `.claude/commands/` esté presente aquí (para poder probarlo), no se deben invocar `/spec /plan /build ...` sobre este propio repo para cerrar sus propias versiones — mezclaría contenido meta del framework con lo que se distribuye como plantilla genérica. El cierre de versión de este repo (`task.md`, `memory.md`, `walkthrough.md`, commit y tag) se hace manualmente, imitando la estructura que la Fase Ship generaría en un proyecto consumidor.

- **[La verificación de un framework de prompts se hace con la IA real, no solo con scripts]** (2026-10-14): con el CLI real se ejecutaron el bootstrap (pide confirmación antes de restablecer `task.md`/`memory.md`, no hace `git init`), `/plan → /build → /test` (imprime el Architect Review con `<evidence>` y `<confidence_score>`, etiqueta `@spec`, 7 tests reales), `run-evals.sh` y una actualización v2.9.0 → v3.0.0 de un proyecto con spec sin IDs, código heredado y un `AGENTS.md` propio (nada protegido cambió salvo la nota de rutas añadida a `AGENTS.md`). Esas pruebas, y no los scripts sintéticos, destaparon cuatro fallos: un eval que pasaba sin que la IA hiciera nada (estado previo), el linter analizando 3.145 ficheros de un runtime empaquetado (ahora respeta `.gitignore`: 19 s y 14.580 hallazgos falsos → 2 s y 55 reales), un `UPGRADE_PROMPT` sin su propia fila en el manifiesto (se detecta comparando `git diff v<anterior>` con el manifiesto) y que `claude -p` ignora los `permissions.allow` de un proyecto sin confianza. Una segunda actualización con descargas reales destapó que una frase condicional dentro de la fila del manifiesto («si el usuario ya añadió evals propios, no los toques») hacía que la IA se saltara la fila entera: lo obligatorio y las excepciones sobre ficheros del usuario van en filas separadas. Detalles de la prueba: un flag variádico (`--allowedTools`) se come el prompt si va delante; hay que pasarlo tras `--`.
- **[El README es lo primero que lee una IA: su inicio debe ser el mensaje de una línea]** (2026-10-15): el uso real del framework es decirle a la IA «Quiero crear un proyecto utilizando el framework dbv-specs-ops que puedes encontrar en github.com/davidbuenov». El README lo enterraba en el 7.º apartado, con un índice que enlazaba viñetas y no secciones. Ahora abre con «Empezar en un minuto» (mensaje + tabla nuevo/existente/actualizar + instrucciones plegadas para la IA) y la instalación a mano es la alternativa.
- **[Un borrador técnico se ejecuta antes de aplicarlo]** (2026-10-14): el borrador de v3.0.0 traía un linter que *compilaba* pero tenía una regex rota (`\vert{}` en vez de `|`, la trazabilidad nunca avisaba), calculaba la raíz desde la ubicación del script (en este repo escaneaba todos los repos vecinos), moría con `UnicodeEncodeError` en la consola de Windows (cp1252), daba falsos positivos con guards y decoradores e incumplía su propia regla. Solo se vio ejecutándolo con casos concretos (en una carpeta de pruebas, no sobre el repo). Un script o una regex de un borrador, venga de quien venga, se prueba con entradas buenas y malas antes de publicarlo; y un linter se aplica primero a sí mismo.
- **[Una regla nueva no puede romper lo que ya funciona]** (2026-10-14): endurecer una regla (IDs de requisito obligatorios, un linter que falla) sobre proyectos ya entregados los rompe en silencio. Cada regla nueva nace con su salida de compatibilidad: obligatoria solo para lo que se escribe a partir de ahora, modo «solo lo que tocas» (`--changed`) para el código heredado, y los ficheros del proyecto del usuario siguen protegidos en `UPGRADE_PROMPT`.
- **[El CI del tap de Homebrew comprueba lo que ve el usuario, no el texto del Cask]** (2026-09-29): Homebrew 7 declaró obsoleto `preflight` en taps de terceros, y el CI del tap de DBV Typst Editor seguía en verde mientras cada usuario veía el aviso. Peor aún: `app_image` pasó a mover el AppImage fuera de `staged_path`, y el comando `typs` de Linux llevaba roto desde entonces, porque el CI solo hacía `grep` sobre el contenido del script. Ahora el CI falla ante un «deprecated» en la salida de `brew install` y ejecuta `test -x` sobre el fichero al que apunta el comando (§6quinquies de `NATIVE_APPS_RELEASE_CI.md`).
- **[Un paso de CI que ejecuta un binario se prueba en WSL antes de confiar en él]** (2026-09-28): al añadir el `.zsync` del AppImage (§6quater), la comprobación con `--appimage-updateinformation` se habría colgado en la CI hasta el límite del job: con `APPIMAGE_EXTRACT_AND_RUN=1` el runtime arranca la aplicación entera en vez de responder. Solo se vio ejecutando el paso en WSL sobre un AppImage publicado. `zsync` se instala sin `sudo` con `apt-get download` + `dpkg -x`.
- **[Una lección de un proyecto derivado se sube al framework y a la plantilla a la vez]** (2026-09-28): el fallo de permisos del `.AppImage` (§6ter de `NATIVE_APPS_RELEASE_CI.md`) apareció en dos apps derivadas el mismo día porque las dos copiaron el mismo `release-linux.yml`. Documentarlo solo aquí no lo arregla en las apps nuevas: el paso se añade también a la plantilla de §9 y al `release-linux.yml` de `dbv-tauri-starter`, que es de donde se copian.

## 🧹 Política de Mantenimiento

*Aplicar en cada `/ship` de tipo Major, o cuando este fichero supere las 200 líneas activas (formato Hot/Warm/Cold en `<context_management>` de `MASTER_PROMPT.md`):*

- **Consolida** decisiones relacionadas en una sola entrada.
- **Archiva** los ADRs antiguos y las lecciones ya internalizadas en el código: muévelos a `memory.archive.md` (créalo si no existe) y deja una línea por ADR: `- (AAAA-MM-DD) <título>: decisión → motivo clave (detalle en memory.archive.md)`.
- **Elimina** entradas que describan decisiones revertidas o ya obsoletas.
- **Objetivo:** mantener `memory.md` por debajo de ~200 líneas activas para que la IA pueda leerlo íntegramente en cada sesión sin pérdida de atención.
